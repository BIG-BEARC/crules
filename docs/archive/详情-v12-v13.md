### 根因与治理方案（为什么总览会滞后，如何避免）

**根因**：

1. **派生数据天然滞后**——README 的文件清单 / 规模表 / 启用决策表全是「实际有哪些文件」的派生物化视图。源变了、派生不会自动变，无刷新触发器必失效（数据库铁律：物化视图无触发器必过期）。
2. **纪律没 dogfood 自己**——MAINTENANCE「触发即更新」只管下游项目的代码索引（新建源文件→更新 indexes），**没套用到模板包自身的元文档**（新建进阶篇→更新 README 清单）。规则管别人，没管自己。
3. **评审盲区 + 归档切断**——v8/v10/v11 评审只盯「新能力落地」，没人回头查总览是否反映；变更事实只存在 archive/评审-vN.md（过程文档），没有「活」的变更日志，下次更新 README 时无从查起。

> **自指盲区**：本包整套哲学（约束不丢失 / 沉淀闭环 / 权威正文单一）就是治这种病的——却只用在下游项目，没用在自己元文档上。**鞋匠的孩子没鞋穿**。最优雅的解法 = **dogfooding**：把模板包自己当项目，套自己的纪律。

**治理方案（分层）**：

| 方案 | 治什么根因 | 成本 | 时机 | 状态 |
|---|---|---|---|---|
| **C 评审加「总览同步检查」** | 评审盲区 | 零 | **立即** | ✅ 评审.md L14 |
| **D 建本包 CHANGELOG**（`docs/CHANGELOG.md`） | 归档切断 | 低 | **短期** | ✅ 已建 |
| **A MAINTENANCE 加「元触发表」** | 派生无触发 / 纪律未套自己 | 低 | **中期** | 缓（设计新机制） |
| **B2 自检 checklist** | 物化视图失效兜底 | 低 | **可选** | 缓（设计新机制） |

> **C+D+A 本质就是 dogfooding**——把 MAINTENANCE / 沉淀闭环套回模板包自身。这也是本包自己教的东西。
