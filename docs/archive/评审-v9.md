## §3 新发现（本轮核对抓到）

### 🟡 M1. `plan-reviewer` 只读工具锁 ↔ 「直接写盘」矛盾（核心，机制未闭环）

- **位置**：`agents/plan-reviewer.md` frontmatter（`tools: Read, Glob, Grep`）+ :30「落盘」+ :43「输出评审文档落盘……**直接写盘**」；`进阶/方案评审闭环.md:56` 流转第3步「plan-reviewer 输出评审文档→落盘」、:76 纪律「不调用任何修改工具（Edit/Write/NotebookEdit/写性 Bash）」
- **矛盾**：
  1. 角色卡 `tools` 只有 `Read, Glob, Grep`——**没有 Write**；
  2. 评审纪律明确「不调用 Write」；
  3. 但工作流程要 plan-reviewer「**直接写盘**」「落盘 docs/评审-plan-<feature>.md」。
  - 三者撞车：plan-reviewer 既无 Write 工具、又被纪律禁止 Write，**它根本写不了盘**。
- **底层机制**（Claude Code subagent）：只读 subagent 的产出是**返回值回到主控**，subagent 自己不能写文件（除非 frontmatter 给 Write）。所以「plan-reviewer 直接写盘」在当前工具锁下**机制性不可行**。
- **建议（唯一可行解）**：把落盘执行者写明为**主控**，机制改为——
  > plan-reviewer 产出评审内容**作为返回值** → 主控**原样落盘** `docs/评审-plan-<feature>.md`，**不得修改评审内容**。

  具体改 3 处措辞：
  - `plan-reviewer.md:43`「直接写盘」→「输出评审内容作为返回值；由主控**原样落盘**（不修改/不过滤）——本角色无 Write 工具，不自行写盘」
  - `方案评审闭环.md` 角色四分表「派发/转交」行职责追加「**原样落盘评审文档，不修改内容**」
  - `方案评审闭环.md:56` 流转第3步「plan-reviewer 输出评审文档→落盘」→「plan-reviewer 输出评审内容（返回值）→ 主控**原样**落盘」
- **性质**：这与 :28「信息隔离非物理绕过」已承认的边界**一致**——subagent 产出必然经主控，独立性靠纪律（主控原样写、不改）保证，而非靠 plan-reviewer 自己写盘。当前措辞掩盖了这个真实机制，按建议写明即可闭环。**不修也跑得通**（主控会自然代写），但写明能避免「plan-reviewer 怎么写不了盘」的实操困惑。

### 🟢 M3. 「可选追加 WebFetch/WebSearch」与静态 frontmatter 措辞不对齐

- **位置**：`方案评审闭环.md:78`「默认 Read,Grep,Glob；方案明确需外部技术查证时**可选追加** WebFetch,WebSearch」vs `agents/plan-reviewer.md` frontmatter 静态 `tools: Read, Glob, Grep`
- **问题**：frontmatter 是静态的，「可选追加」实际靠用时**手改角色卡 frontmatter**，但正文没点明这一点，读者可能以为有运行时开关。
- **建议**：措辞改为「需联网查证时，在角色卡 frontmatter 的 `tools` 追加 `WebFetch, WebSearch`」（点明是改角色卡，不是运行时切换）。
