## 历史详情（v18 二审，审计保留）——`/review-review` 首次实战 + superpowers 调研

> v18 二审详情降级为历史（v18 复盘已含其结论）。原文保留审计链。

> 本轮是对 v18 修改方案（[`修改方案-v18.md`](修改方案-v18.md)）的**独立第三方复审**，由 `/review-review` 机制首次实战执行。**本轮只出评审意见，未落地任何 hooks 代码**——落地路径待需求方据本评审定。

### 一、复审怎么做的（机制验证）

- **独立 subagent 复审**：派独立上下文 `general-purpose` subagent（看不到本对话历史，只喂 v18 方案 + 评审.md + crules 源文件读权限），按 `/review-review` 设计产出结构化 meta-review，主控原样呈现不过滤。
- **主控补做 superpowers 调研**（需求方建议）：查 superpowers 的 hook 实现，看成熟插件怎么做提交/破坏性纪律。
- **transcript 格式实测**：在本会话 transcript 文件上验证 R2 的格式假设（JSONL 确认；`"role":"user"` 无空格形式可命中，但顶层 role 实为 null，字段路径需 hook 运行时确认）。

### 二、独立复审结论（原样采纳）

**方向 ✅**：A 的诊断（dogfooding 第四盲区）成立且精彩——核验 INVARIANTS.md L35「只有文档没测试=软约束」、评审.md v16「纪律写了≠生效」、全包 grep `hook|PreToolUse` 在 v18 前零命中。D/C 暂缓、hook1/2 先上 hook3 缓办、A4 点名资产保护坑——全对。

**实施 🔴（R1-R4，必须改才能落地）**：

| # | 问题 | 独立复审建议 |
|---|---|---|
| **R1** | git-commit-guard 只看「最近一条 user 消息」**既误放行也误拦截**。「这 commit 信息不错」→ AI 自动提交被放行；用户发「提交」后 AI 跑 git status 再说别的→真 commit 被拦（授权窗口被中间对话冲掉） | 改扫最近 N 条消息；或 deny 时把授权意图回灌给 Claude 让它回头问用户 |
| **R2** | transcript 格式假设（`grep '"role":"user"'`）未验证 + **fail-open**（解析失败静默放行）。安全 hook 默认应 fail-safe=deny | 实测格式 + jq 结构解析 + 解析失败改 deny |
| **R3** | `set -euo pipefail` + grep 管道退出码坑——grep 无匹配 exit 1，set -e 下脚本可能异常退出 | 去掉 set -e 显式处理，或每个 grep 用 if 包裹，测四路径 |
| **R4** | destructive 正则是**封闭子集**，漏 `rm -fr`/`rm -r`/`git stash drop`/`chmod -R`/`git checkout --` 等。CLAUDE.md §二 L73-78 是开放枚举。**hook 让人以为全兜住，实际漏一地，比没有更危险（虚假安全感）** | 对照 §二 L73-78 补全 + **诚实声明「hook 只覆盖子集，其余靠 prompt」** |

**可商榷 🟡（Y1-Y6）**：jq 依赖未声明 / A5「互为兜底」措辞应改「hook 是 §二 硬执行，覆盖是子集」/ A6 查三表自洽 / A7 团队张力（不进 git=团队各装） / ask 的 UX 未验证 / 维护原则补「改红线同步改正则」。

**遗漏边界（6）**：transcript_path 是否在 stdin payload / 空 stdin 退出码行为 / **hook 只锁 Bash 漏 Edit/Write/MCP** / chmod +x 在 cp 后保留性 / **A4 老项目 JSON merge 策略未定义** / review-review 工具锁跑不了 Bash 验证 hook。

### 三、superpowers 调研发现（关键，改变权衡）

查 `~/.claude/plugins/installed/superpowers/hooks/`：

- **superpowers 只用 SessionStart hook**（注入 using-superpowers skill 内容），**不用 PreToolUse 拦 git/破坏性操作**。
- 它的**提交纪律纯靠 skill + CLAUDE.md prompt**——与 crules **现状完全一样**。
- `session-start` 脚本揭示了已验证事实：`set -euo pipefail` 在 hook 可用（关键在显式控制退出路径）；hook 输出 `hookSpecificOutput` 嵌套 JSON 格式权威（v18 方案的 `permissionDecision` 结构与之同构，机制成立）。
- **但 superpowers 的 hook 不读 transcript**——它只做 context 注入，**没有可借鉴的「transcript 授权词解析」逻辑**。

**结论**：**没有现成的、被验证过的 PreToolUse git/破坏性 hook 可抄**。superpowers 作为成熟插件有意回避这层，**侧面印证 R1-R4 的坑真实——尤其是 R1（授权判定），成熟项目也没解决，干脆不做**。crules 并不比 superpowers 落后（两者提交纪律都靠 prompt）。

### 四、主控综合评审意见

**最大洞察（自指警示）**：独立复审最锐利的一句——「**方案文档把 hook 脚本写得像成品，实际是未验证草稿；这本身也是『写了≠生效』的变体（dogfooding 的微妙复发：自信贴完整脚本让人以为可执行）**」。crules 治的就是「自信贴文档没验证」，v18 方案自己这么干了。**这一条比 R1-R4 更值得记取。**

**对 v18-A 的评审意见**：

1. **方向认可**：hooks 确是 dogfooding 盲区，诊断成立。
2. **实施否决（当前形态）**：R1-R4 是真问题，当前脚本不可直接落地。尤其 R1（授权判定）是行业级难题，superpowers 都回避——crules 贸然写复杂 hook 可能是「为硬而硬」，引入 4 项债务换不确定收益。
3. **建议路径（供需求方定，非决议）**：
   - **destructive-guard 可考虑先上**——它不依赖 transcript 解析（只 grep 命令字符串），R4 补全正则即可，收益明确（破坏性操作二次确认）、风险低；
   - **git-commit-guard 建议暂缓或改设计**——R1 授权判定难可靠，与其做不可靠的 transcript grep，不如保持 prompt（现状已与 superpowers 对齐），等更可靠机制（如 Claude Code 原生的提交授权 UI）；
   - 若坚持两个都上，脚本须标「草稿·待真实会话实测」，R1-R4 落 TODO，**诚实声明 hook 覆盖是 §二 子集**（治 R4 虚假安全感）。
4. **小项（删版本号 v1.1）**：无风险，可独立做，不与 A 绑。

**本轮不落地**——落地路径属需求方决策（选哪个建议路径），评审只出意见。

### 五、机制产出：`/review-review` 实战验证

本轮证明 `/review-review` 机制有效：主控预判到 R1/R4，但**漏了 R2（fail-open）和 R3（set -e 坑）**，独立 subagent 补上。这正是设计目的——结构化消除主控确认偏差。

> **一个边界被发现**：`/review-review` 的 subagent 工具锁是 `Read, Glob, Grep`（见 `commands/review-review.md`），**跑不了 Bash 实测 hook**。本轮 transcript 格式实测是主控补做的。落地验证（hook 真生效）靠人跑四场景，review-review 只审文档/代码静态正确性——这个边界已在独立复审「遗漏边界 6」记录，后续应写进 review-review.md 的「注意」段。

## 历史详情（v15，审计保留）——使用方式简化 + 老项目支持

### 痛点（为什么现在麻烦）

| # | 痛点 | 说明 |
|---|---|---|
| 1 | 选规模门槛 | 用户要先懂轻量/标准/重度区别才能决定复制什么；新用户不知自己算哪档 |
| 2 | 分散 cp 易错 | 手动复制到 4 个位置（项目根 / `.claude/agents` / `.claude/memory` / `.claude/commands`），漏一项就 latent 故障——正是 v13 总览滞后的温床 |
| 3 | 逐篇判断启用 | 6 篇进阶各带「启用条件」，要逐篇读才能定 |
| 4 | 附录填空负担 | 项目附录一堆【必填】，填不齐用不好 |
| 5 | **老项目零覆盖** | README 隐含「新项目从零复制」，已有 CLAUDE.md 的老项目怎么用——完全没说（缺口） |

### 方案

**主推：`/crules-init` slash command**（`commands/crules-init.md`）——把「选择 + cp + 合并」交给命令，用户只答 2–3 问。

- 自动检测新/老项目（根目录有无 CLAUDE.md）
- **新项目分支**：问规模 / 技术栈 → 自动 cp 全部到位 → 引导填附录
- **老项目分支**：读现有 CLAUDE.md → 列冲突 → 取舍 → 合并（见下）
- 零外部依赖（AI 执行 cp），契合纯文档包定位

**配套**：
- README 叙事反转——不教「选规模复制」，教「一条命令全装，进阶自带门控默认关，用到才开」
- 附录减负——【必填】只留 项目名 / 技术栈 / 命令 三项，其余降【可选】

### 老项目合并流程（4 步，`/crules-init` 老项目分支自动化）

1. **体检**：AI 读老 CLAUDE.md + crules CLAUDE.md，列**冲突条款**（提交策略 / 双 Gate / 验证证据 / 不虚构等）
2. **取舍**：用户逐条定——保留老的 / 用 crules 的 / 融合
3. **合并**：AI 据取舍生成合并 CLAUDE.md（老规则在前 + crules 纪律，冲突按取舍）
4. **附录对齐**：附录填空与老项目实际对齐，不重复造

> 最大坑：**规则冲突**（如 crules「人工提交」vs 老项目「自动提交」）。体检必须显式列冲突，**禁静默覆盖**——否则等于把老项目规则吞了。

### 老项目知识库文档处置（合并流程的第 5 维）

v15 合并 4 步只讲 CLAUDE.md；老项目还有一堆**历史文档**（需求 / 设计 / 接口 / 踩坑 / 旧规范），是知识库但不一定实时。

**核心矛盾**：**过时文档比没文档更危险**——没文档 AI 至少不照做；过时文档 AI 照错的做还自信（有"文档依据"），测试还可能绿着掩盖。即 v11 续讲的**约束漂移**。故处置核心不是"要不要保留"，是"**如何防止过时文档误导 AI**"。

**处置模型：分级 → 纳管/隔离 → 迁移即验证 → 活文档保鲜**

**1. 分级**（按时效敏感性）：

| 层 | 例子 | 漂移风险 | 处置 |
|---|---|---|---|
| 时效敏感 | 架构 / 接口 / 约束 / 状态 | 高（最危险） | **验证后**才让 AI 信 |
| 知识沉淀 | 为什么 / 踩坑 / 决策 | 低（历史事实不变） | 相对安全，可直接用 |
| 过程性 | 会议纪要 / 中间稿 / 废弃方案 | 高（易误导） | 归档，**不进 AI 默认视野** |

**2. 信任分级**（类比 business-rules 可达性）：默认老文档 = **L0 历史快照**（未经当前代码验证，当"线索"不当"事实"）；经验证 = L1；纳入活文档机制 = L2。**AI 引用 L0 前必须验证**。

**3. 纳管 / 隔离**：
- **纳管**：高价值老文档迁入 crules 载体——业务事实→`business-rules.md`、技术不变量→`INVARIANTS.md`、决策→`decisions/`、代码模式→`patterns.md`。迁入即纳入 MAINTENANCE 维护机制。
- **隔离**：过程性 / 易误导的移 `archive/`（留溯源不删，但不进 AI 默认视野）。

**4. 迁移即验证**：纳管不是搬运——每条迁入须当下对照代码 / 需求方确认仍成立，**不确认不迁**。迁的过程就是漂移检测。

**5. 活文档保鲜**：迁入后靠 MAINTENANCE「触发即更新」+ INVARIANTS「定期收敛」防再漂移。

> **矛盾文档**开 `decision` 记"以哪个为准 + 为什么"（v11 生命周期规则），不静默二选一。
> **这又是 dogfooding**——v10（business-rules）/ v11（INVARIANTS + 生命周期 + 活跃历史分离）/ v11 续（约束漂移）整套知识层治理，本来就是为"知识库会膨胀会漂移"设计的，老项目历史文档正是它要治的病。
