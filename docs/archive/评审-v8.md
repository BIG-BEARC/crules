## §1 焦点：方案评审闭环缺口（🔴 结构性，本轮新发现）

### 1.1 三层现状（前三轮核实）

| 层面 | 现状 | 问题 |
|---|---|---|
| **计划文档**（PRD / spec / 方案 / plan） | 把关 = 需求方**人工双 Gate**；主控自产自交，**0 agent 评审**（工程化流程 §2:19、CLAUDE.md §3:108–123、Agent编排:108） | 连「自己评审自己」都没有，只有人确认；比 self-review 还弱一层 |
| **代码** | 唯一独立评审角色 `reviewer`（Agent编排:43），但①审代码不审计划②由**主控派发**③结论**经主控复核**才上报（Agent编排:90–96） | 半独立；不碰计划；结论被主控稀释 |
| **评审纪律** | 「只评审不修改」无明文。仅 CLAUDE.md §3 任务分类表（98）把「审查」标为「不改代码」（默认行为，非硬纪律）；专门审查篇无此条；无「审查→修复」衔接授权（对比诊断有 CLAUDE.md:106） | 边界情况（评审者顺手改、评审后直接动手）无规则抓手 |

### 1.2 期望（需求方提出）

对**实现方案**做**完全隔离的第三方评审**：评审者既非计划产出者、也非派发者/复核者、无任何利益关联 → 输出评审文档并**落盘** → 评审文档**完全遵守「只评审、不修改；只给建议/方案、不进行实际代码操作」** → 产出者读评审逐条回应（不合理给原因 / 合理看有无更优方案）→ **用户裁决改哪些** → 改完第二轮评审 → 循环到「评审完全通过 + 用户确认」才进下一阶段。

### 1.3 一个技术边界（已与需求方对齐）

> Claude Code 里**所有 subagent 都由主对话（主控）派发**（Task tool），物理上不存在「绕过主控的第三方」。需求方要求的「无利益关联」靠**信息隔离**实现，对方案评审足够：
>
> - 派发一个**独立上下文** subagent（看不到主对话历史）
> - prompt 里**只喂方案文档成品**，不喂「方案怎么产的、谁的倾向、讨论过程」
> - 评审结论**不经主控复核过滤**，直接落盘
> - 这条与现有代码 `reviewer` 的「主控复核」（Agent编排 §主控复核责任）**显式区分**：代码 reviewer 那条保留，方案评审**不走复核**
>
> = 评审者只看到方案成品的独立 agent，不护短、结论不被稀释。这是**信息层完全隔离**，非**组织层不经主控**。若要求物理绕过主控，Claude Code 架构做不到——本建议以信息隔离为准。

## §2 落地建议（取值已按需求方确认）

### 2.1 角色四分

| 角色 | 由谁担任 | 职责 | 关键约束 |
|---|---|---|---|
| **方案产出者** | 主控（或 spec-kit） | 产方案文档；读评审文档**逐条回应**：评审不合理→给原因；合理→有无更优方案，有则给方案+原因 | 不自行改方案，等用户裁决 |
| **第三方评审** | 新增独立 subagent `plan-reviewer` | 只读方案，输出评审文档落盘 | **只评审、不改码、不产方案、不调用修改工具** |
| **派发 / 转交** | 主控 | 派发评审 subagent、转交评审文档给产出者与用户 | **不过滤评审结论** |
| **裁决** | **用户** | 确认改哪些；确认是否通过、是否进下一阶段 | 唯一有权拍板 |

### 2.2 闭环流转（7 步）

```
1. 方案产出者输出方案文档（方案 Gate 产物 / PRD / spec）
2. 主控派发第三方评审（独立上下文 subagent，prompt 只喂方案成品）
3. plan-reviewer 输出评审文档 → 落盘 docs/评审-plan-<feature>.md（v1）
4. 方案产出者读评审文档，逐条回应：
     · 评审不合理 → 指出 + 给原因
     · 评审合理   → 有无更优方案？有 → 给方案 + 原因
5. 用户确认改哪些（裁决）
6. 改完 → 第二轮评审（评审-plan-<feature>.md v2）→ 循环
7. 直到「评审无 🔴 + 用户明示通过」→ 进实施
```

### 2.3 评审纪律（钉死，写入角色卡 + 评审文档头）

`plan-reviewer` 角色卡与每份评审文档头部均声明：

> **只评审、不修改**被评审方案 / 代码；**只输出**建议 / 方案 / 发现；**不调用**任何修改工具（Edit / Write / NotebookEdit / 写性 Bash）。

角色卡 frontmatter 用 `tools` 字段锁只读（示例）：

```yaml
---
name: plan-reviewer
description: 对实现方案做完全隔离的第三方评审；只评审不改码、不产方案
tools: Read, Grep, Glob, WebFetch, WebSearch
---
```

### 2.4 落地骨架

| 项 | 内容 |
|---|---|
| **新增独立篇** | `进阶/方案评审闭环.md`（被 CLAUDE.md §3、工程化流程 §4、审查与复核纪律 §两阶段审查引用） |
| **新增 agent 角色** | `plan-reviewer`（区别于代码 `reviewer`），`agents/plan-reviewer.md` 加角色卡，frontmatter 锁只读工具 |
| **Gate 位置** | 插在**方案 Gate 之后、实施之前** = 方案产出 →〔新〕第三方方案评审 → 通过 → 实施。本质是方案 Gate 的强化（独立 agent 替代/增强人工确认） |
| **文档落盘** | `docs/评审-plan-<feature>.md`（v1/v2 迭代，与本文档 `docs/评审-vN.md` 同风格） |
| **与代码评审区分** | 本机制审**方案**（实施前）；`reviewer` 审**代码**（实施后）。两者角色、纪律、时机均不同，不混用 |

### 2.5 三个设计点（取值）

| 设计点 | 取值 | 理由 |
|---|---|---|
| **适用范围** ✅ | 大需求（新页面 / 跨模块 / 多端 / 大重构）走；极简（单字段 / 文案 / 明显单点修复）**跳过** | 与工程化流程 §1「极简改动不适用本流程」一致；单字段也派评审 agent 成本不值 |
| **方案产出者** ✅ | 保持**主控**产出（或 spec-kit） | 评审者独立即满足「无利益关联」；要极致分离再拆专门 planner，轻量起见不必 |
| **「完全通过」标准** ✅ | **无 🔴 = 技术通过**，但仍**须用户确认**才进实施 | 防评审与产出者达成共识、但方向本身错；用户是领域专家，终裁归用户 |
