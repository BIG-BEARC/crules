# 通用项目规则模板包 · 评审文档（v11）

> **本版性质**：延续 v10。v10 的「业务可达性知识层」（`business-rules.md` 载体 + 补充 SOP）**不变**。本版承载 v10 之后多轮深挖的**知识层工程化治理**——约束分治、膨胀防御、生命周期、分域演进，回答"知识层在规模增长和时间推移下怎么不塌"。
> **触发案例**：一个真实项目里「ConnectManager 在 Win7 不可靠」已修复，却在后续改另一个问题时被再次修坏（回归）。根因是约束丢失（compaction 丢"为什么"+ 反向推理 + 不声明不变量）。本版是该案例的系统性解法。
> **符号**：🔴 重要 / 🟡 中等 / 🟢 小优化。本文档仅为评审，未改动任何规则或代码文件。

---

## §1 焦点：知识层会塌吗？

v10 提的 `business-rules.md` **隐含假设规则静态一致**。但现实里规则会演变、会冲突、会膨胀。不治理，知识层会塌成三种废形态：

| 塌法 | 表现 | 后果 |
|---|---|---|
| **自相矛盾的废纸** | 新老规则打架，没有冲突检测 | AI 照错的做，比没有更糟 |
| **噪声淹没的大文件** | 规则堆一起，找不到相关的 | AI 干脆不信文档，回凭印象 |
| **漂移的错误约束** | 业务变了文档没变 | 有约束但是错的，测试还绿着掩盖 |

本版给治理机制，让知识层扛住规模和时间。

## §2 约束分治：不止"业务规则"一类

图里用「不变量」**泛指所有约束**，不精确。约束分 4 类，**载体和检查各不同**——一锅炖进"不变量清单"是隐患：

| 类别 | 定义 | 破坏后果 | 载体 | 检查 |
|---|---|---|---|---|
| **不变量 invariant** | 任何时刻任何路径都必须成立 | 破坏即 bug | `INVARIANTS.md` | **测试/断言（硬拦）** |
| **假设 assumption** | 代码依赖的外部条件 | 假设错就 bug | 契约/接口文档 | 契约测试/mock |
| **业务规则 business rule** | 业务真实运转方式 | 误判可达性 | `business-rules.md` | 审查 Gate |
| **决策 decision/ADR** | 为什么选 X 不选 Y、放弃了什么 | 重新推理推翻已否决方案 | `decisions/` | 提案前读 |

**对应两类案例，两套载体**：
- v10 的 `business-rules.md` → 管**业务可达性误判**（称重 case）
- 本版新增 `INVARIANTS.md` → 管**技术回归**（ConnectManager/runOnce case，正是图里的场景）
- 两者**复用同一套治理**（§3–§6），但载体分开

所以 v10 的 business-rules 只是约束的一类；技术约束（不变量/假设）是平行另一条线。

## §3 约束丢失场景：不止 compaction

| 场景 | 机制 | 对治 |
|---|---|---|
| compaction 有损压缩 | 丢"为什么" | decision 记推理链 |
| 换会话/换人 | 上下文不继承 | 文档落仓库 |
| 模型升级换代 | 新模型不知旧约束，"自信重推" | Gate 强制先读约束 |
| 子代理盲区 | 看不到主控上下文 | 派发时 prompt 注入约束 |
| 人自己忘了 | 半年后没人记得 | 约束文档 + 溯源 |
| 重构改名/移路径 | 文档"关联代码"失效 | 规则写关联，改名同步 |
| **约束漂移·文档过时** | 业务变了文档没变 | **最难，见下** |
| AI 自信重推 | 凭代码现状反向推断 | 约束当过滤器非备忘 |
| 噪声淹没 | 规则太多相关被淹没 | 分域+索引（§4） |

**🟡 约束漂移比丢失更危险**：丢失是"没约束"（AI 至少谨慎）；漂移是"有约束但错的"（AI 照错的做，比没有更糟）。且漂移**不自动暴露**——测试锁的是旧约束，约束该变没变时测试反而绿着掩盖。**漂移只能靠人肉收敛（季度复盘），无银弹。**

## §4 膨胀防御：分域 + 索引 + 标签检索

### 4.1 膨胀判据：看活跃数，不看总数

- ❌ 一个域**总条数**多 = 不一定膨胀（若大多归档）
- ✅ 一个域**活跃规则数**多 = 真膨胀（该再拆子域）
- 50 条活跃 + 200 条归档 ≠ 膨胀；50 条活跃混一起 = 膨胀

### 4.2 演进式分域（修正 v10"出生就分域"的绝对化）

> 准确说法：**出生就建 INDEX（分域机制），域本身按痛感分裂（实体）。** 强行一开始划 10 个域 = 10 个空文件。

- **冷启动**：单文件 `rules.md` + INDEX 先行（INDEX 比域更重要）
- **分裂触发线**：单文件 >200 行 / >15 条 / 出现 2-3 个混杂业务主题
- **域跟业务实体命名，不跟技术层**（称重/库存/核销，非 网络/存储/UI）

### 4.3 跨域：分清两种，处理不同

| 跨域类型 | 例子 | 处理 |
|---|---|---|
| **业务组合跨域**（两业务实体偶尔同现） | 称重+核销 | **单一归属+反向引用**（默认）：判主域（不成立时谁先出 bug）→ 实体放主域 → 其他域 INDEX 加指针 → 规则带「涉及域」标签 |
| **横切关注点跨域**（一主题渗透所有域） | 权限/审计/日志 | **独立横切域**（`cross-cutting/auth.md`） |

### 4.4 新域诞生

默认塞现有域；**新建触发线**（满足任一）：独立新领域 / 目标域将超规模 / 与所有现有域强行关联。域可合并/分裂（动结构开 decision 留痕）。

### 4.5 升维：放弃完美分类，用标签+索引检索

三个"放哪"问题（跨域/新业务/初始）的共同根因 = **想用物理位置解决检索问题**。树形分类永远会被跨域和新增打脸。终极解：**改用标签+索引检索，让检索不依赖物理位置。** 规则带多维标签（涉及域/适用场景/关联代码/来源），INDEX 按多维度建指针——物理放哪就不重要了。

**INDEX 样例（按域 + 跨域指针双视图）：**
```markdown
# rules/INDEX.md  （只索引活跃规则）
## 按域
| 域 | 文件 | 活跃条数 | 一句话 |
|---|---|---|---|
| 称重 | weigh.md | 3 | 字段回传/试算/拦截 |
| 权限(横切) | cross-cutting/auth.md | 1 | 渗透所有域 |
## 跨域指针（实体在主域，这里只指针）
| 规则 | 主域 | 涉及域 |
| WR-WEIGH-005 核销场景称重 | 称重 | 称重,核销 |
```

**带多维标签的规则条目：**
```markdown
## WR-WEIGH-005 核销场景 X 不触发称重
- 涉及域：称重(主), 核销
- 适用场景：核销类型 X
- 结论：核销 X 菜品不含称重菜
- 可达性判定：若审查发现"核销 X 绕过称重锚定"→ 不可达
- 关联代码：redeem_x.dart, weigh_service.dart
- 来源：称重审查误判 case
```

## §5 生命周期：不塌成矛盾废纸

### 5.1 状态机

`草稿 → 生效 →（被取代 / 失效）→ 归档`

### 5.2 写入冲突 Gate（半自动，防只增不改）

新增一条规则时强制：起草 → **先读同域所有活跃规则** → 逐条标关系（一致/冲突/无关）→ 冲突的转 decision → 人确认 → 入库（标"取代 WR-XXX"）。

**规则必须带前提/适用范围**：很多"矛盾"其实是适用范围不同（A 场景规则 X、B 场景规则 Y，表面打架实际互补）——写清前提，矛盾才好识别。

### 5.3 矛盾解决

- 矛盾**不删**，旧规则标「⚠️ 被 WR-YYY 取代 + 原因 + 日期」
- 开一条 `decision` 记"为什么新取代旧"——下次不再纠结
- 规则文件只留极简指针，长篇"为什么"放 `decisions/`

### 5.4 定期收敛（防漂移，§3）

MAINTENANCE 触发表加「业务大版本/季度复盘 → 扫一遍活跃规则，失效的标失效、矛盾的转 decision」。**这是漂移的唯一对治**（人肉，无银弹）。

## §6 生命周期 ≠ 膨胀：活跃/历史分离

> 表面矛盾：§4 说防膨胀，§5 说只增不改——不越胀越大？
> **不矛盾**：膨胀危害来自"AI 读到多少无关内容"。只要历史**不进常规检索路径**，保留再多也不膨胀。

### 6.1 物理分离（分文件，推荐）

```
memory/rules/
├── INDEX.md            # 只索引活跃
├── weigh.md            # 活跃
├── redeem.md
├── cross-cutting/auth.md   # 横切
└── archive/            # 归档区，AI 常规不读
    └── weigh.md        # 被 004 取代的 002 等
```
AI 加载 weigh.md 不碰 archive/，**token 零占用**。只有溯源才翻 archive。

### 6.2 三条配套

- **INDEX 只索引活跃**（归档不进主表）
- **取代指针指向 decision**（规则文件不留长篇）
- **归档淘汰线**：归档 N 月 + 无引用 → 可移除（decision 留痕）

### 6.3 🟡 诚实限制：机制本身需人维护

分离/INDEX/淘汰都要人维护，没人维护照样塌。**这和代码同构**：没持续重构的代码会腐烂，没持续治理的规则库也会。**无任何机制免维护**——治理是降低腐烂速度，不消灭维护责任。机制 + 定期人肉，缺一不可。

## §7 完整文件结构（整合 §2–§6）

```
memory/
├── rules/                  # 业务真实规则（业务可达性，v10）
│   ├── INDEX.md            # 只索引活跃，双视图（按域+跨域指针）
│   ├── weigh.md            # 活跃
│   ├── cross-cutting/auth.md   # 横切关注点
│   └── archive/            # 归档（常规不读，溯源才翻）
├── INVARIANTS.md           # 技术不变量（技术回归，本版新增，对应 ConnectManager 类）
├── decisions/              # 决策/ADR + 取代记录（"为什么"，防 compaction 丢推理链）
└── （patterns.md / NAVIGATION.md / MAINTENANCE.md 既有）
```

四类约束（§2）→ 四个载体，共用 §3–§6 治理。

## §10 结论

- **v10（知识层）+ v11（治理层）= 完整的约束外化机制**。v10 解决"要不要外化"，v11 解决"外化后怎么不塌"。
- v11 的四根支柱：**约束分治**（4 类不同载体）、**膨胀防御**（分域+索引+标签检索）、**生命周期**（状态机+冲突 Gate+定期收敛防漂移）、**活跃/历史分离**（生命周期不膨胀）。
- 关键认知：知识库和代码同构——**没治理的规则库会像没重构的代码一样腐烂**；任何机制都不免维护，治理是降速不是免维护。
- 尾巴侧：**M1 + N1/N2 仍是最该先收的**，与本主题无关。
