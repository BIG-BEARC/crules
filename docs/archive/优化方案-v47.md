## 四、批次一：C1 — deny-list 5 向量修复（🔴 先行快赢）

**改动文件**：[hooks/test_deny_list.py](../hooks/test_deny_list.py) + [hooks/deny-list.py](../hooks/deny-list.py)

### 4.1 五个向量（08-18 外审实测，git 行为已在临时仓库验证）

| # | 向量 | 根因（行号） | git 实测 |
|---|---|---|---|
| 1 | `find … \| xargs rm -rf` | [deny-list.py:121](../hooks/deny-list.py) `paths` 空集 → `all([])` 空真恒过 | xargs 执行期注入路径，删任意文件 |
| 2 | `git branch --delete --force x` | [:102](../hooks/deny-list.py) 只匹配字面 `-D`，漏长选项等价拼法 | 未合并分支强删成功（`-d` 拒删对照成立） |
| 3 | `git branch -d -f x` | 同上，分离旗标拼法 | 同上 |
| 4 | `git push -fv origin main`（`-fq` 同） | [:90](../hooks/deny-list.py) 词边界正则只认独立 `-f` token | 捆绑短旗标 git 接受，与独立 `-f` 同效（dry-run 验证） |
| 5 | `git checkout -qf main` | [:79](../hooks/deny-list.py) token 集合比较 `"-f" in flags`，捆绑 `-qf` ≠ `-f` | 脏工作区未提交改动被丢弃（实测） |

**机制归因**：向量 2/3 = 旗标等价拼法枚举不完备；向量 4/5 = **自家基建未用透**（[parse_flags](../hooks/deny-list.py) 已拆捆绑短旗标且 `git clean` 在用，push/branch/force_switch 三处仍做字面比较）；向量 1 = 空路径集 vacuous truth（空操作数 `rm -rf` 在直接调用下无效果、典型场景即 xargs/stdin 注入——按 deny-by-default 拦截，属策略选择）。v38「对抗样本库的绿 ≠ 防线的绿」第五个数据点。

### 4.2 修法（红→绿流程）

1. **先加 5 个 fixture 确认红**（对抗样本库纪律：新增绕过先加 fixture 再修名单）；
2. `push` / `branch` / `force_switch` 三处旗标判定**统一走 `parse_flags`**（拆捆绑短旗标）：
   - push：`'f' in short or 'force' in longs`（`--force-with-lease` 是长选项，天然不受影响）；
   - branch：`('D' in short) or (('d' in short or 'delete' in longs) and ('f' in short or 'force' in longs))`；
   - force_switch：拆捆绑后判 `-f`，保留 `-b/-c/-s` 建分支例外（既有 fixture 决策）；
3. `rm`：`paths` 为空集直接拦（空操作数 = xargs 注入信号；策略性 deny-by-default，非事实断言——见 §八误拦处置）；
4. **裁定项（2026-08-20 需求方裁定 B：force 信号即拦）**：`git push -fn` / `-nf` / `-f -n` / `--dry-run --force` / `-n +refspec` / `--delete -n` 一并**拦**——push 三条规则（force / delete / +refspec）维持「信号即拦」零交互项，**不设 dry-run 豁免**。与 `git clean -n` 放行的不对称有真实理由：`clean -nd` 是 AI 提议删除前的正当诊断（v39 修的正是这个误拦），`push -fn` 非任何常用诊断路径、强推探测归人工。头注按 v40 字符串误拦先例文档化此取舍，fixture 锁定；
5. **顺带 FP 修复（2026-08-20 实测发现，v47 补）**：重定向 token（`2>&1` / `2>/dev/null` 等）被当作 path 进 rm 白名单判定——`rm -rf /tmp/x 2>/dev/null` 误拦。修法：rm 路径判定前剥重定向形态 token（`^\d*[<>]` 开头），fixture 双向锁定（白名单路径+重定向 → 放；非白名单+重定向 → 仍拦）。

| deny-list 修法引入误拦 | fixture 回归网（既有样本 + 新增，数量以实施时基线为准），误拦走白名单调整（头注既有声明）；`rm` 空操作数拦截按 **deny-by-default 策略**表述（空操作数在 deny-list 语境高度可疑、典型即 xargs 注入），非"直接调用必报错"式事实断言，可能误拦无操作数 no-op，误拦走白名单或人工执行 |
| 回退 | 回退不再以"每批独立 commit"为前提：实施全程不自动 commit，若需求方未逐批授权提交，回退 = 未提交 diff 分块 / 补丁文件 / 人工逆改；**若需求方在批间授权提交，则恢复「单批 git revert」简单回退路径**（两条路径并存，按当时授权状态取用）；批次二、三改同一批文件（CLAUDE.md/工程化流程），单独回退后一批可能牵连前一批段落，回退前先核 diff 相邻性；plugin 侧回退后需重新 `plugin update` + cache grep 验证（cache 不随 git revert 自动回退） |

## 九、实施顺序与放行

批次一 → 二 → 三 → 四，**逐批放行**（每批完成即停下汇报验证证据，需求方确认后进下一批）；每批完整走「实施 → 验证 → 评审轮登记」。**Changelog 口径（锁定）**：v47 一个 umbrella 轮次，四批在该轮内分条记状态，不拆 v47.1/v47.2。全程不自动 commit——各批验证通过后等 `commit` / `push` 指令。
