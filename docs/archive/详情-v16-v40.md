1. **`disable-model-invocation:true` 是解 P2 的原生开关**——command 存在但不被模型主动触发（`-p` 会话 NOT FOUND，`details` 收录）= 纯显式发起，正好让 crules-init 不误推销。
2. **plugin 把 `commands/*.md` 也归为 "Skills"**（details Skills(2)）——command/skill 同源再印证（呼应 `--disable-slash-commands`="Disable all skills"）。
3. always-on 成本 ~62 tok/session（2 组件），可接受。

### 三、概念澄清（关键误解修正）

**plugin 和 skill 不是同一层级**：

- **skill** = 能力单元（一个 SKILL.md）
- **plugin** = 分发容器（装 skill+command+agent+hook+MCP），带命名空间+版本+一键装/卸
- **plugin 里含 skill，不是对立关系**。superpowers = 1 个 plugin 装 14 个 skill。

故 v21 推荐「plugin 化」≠「别用 skill 用 plugin」，而是「能力仍写成 skill/command，但打包成 plugin 分发」。裸 skill 方案丢失的正是 plugin 容器层的命名空间+分发机制。**crules 该纠结的不是「skill 还是 plugin」，是「能力裸放、还是装进 plugin 容器」。**

### 四、本地使用确认（用户需求）

用户需求：plugin 目前纯本地、不团队共享。**实测证实可行**：

| 选择 | 取值 | 效果 |
|---|---|---|
| marketplace 源 | 本地路径（`~/Downloads/ai-code/crules`） | 只在本机有效，天然不共享 |
| install scope | `user`（默认） | 声明进 `~/.claude/settings.json`，不进任何项目 git |

本地用 plugin **仍享全部优势**（命名空间/一键装/disable-model-invocation/版本）。**注意**：plugin 从源 copy 到 cache，改源后须 `claude plugin update` 同步（update 链路未实测，落地时验证）。将来要共享：源改 git repo + scope 改 project 即可，平滑升级。

### 五、决议

- [`重构方案-v20-skills.md`(重构方案-v20-skills.md) 待修订为 plugin 版
- **P1 必修**：update-memory description 改回「全量索引同步」（原文语义）

| 提交纪律 | prompt + `finishing-branch`：实施完成问用户选选项，**选中即自动执行 git**（merge/PR） | prompt（§二 要求显式 commit/push/提交**关键词**才执行） | **触发点不同**（选项触发 vs 关键词触发），crules 更严；但都靠 prompt + Claude Code 原生工具确认，**无 hook 层差距** |
| 破坏性操作 | 纯 prompt + Claude Code 自带工具确认 | 纯 prompt + 同 | **无**——已对齐 |

**结论**：crules 与 superpowers 在提交/破坏性纪律上**都靠 prompt + 原生工具确认，无 hook 层差距**（仅提交触发点不同：crules 要求关键词，superpowers 选项即执行——crules §二 已用优先级链覆盖此差异）。不存在"hooks 盲区"该补的差距。v18-A（git-commit-guard + destructive-guard）整体撤销——不只 git-commit（R1 两难），destructive 也撤（依赖系统已有防护的第二层，边际收益<维护成本）。

- **小项**：删 `CLAUDE.md` 版本号 v1.1 行（已删）。

### 二、为什么绕了三轮（根因复盘）

git/hook 这块三轮绕弯、最终"什么都不加"，根因是**方法论错误**，非偷懒或乱写：

| 根因 | 表现 |
|---|---|
| **1. 没先验证参照物就设计方案**（最致命） | 第一轮就断言"该加 hook"，全程没查 superpowers。直到第三轮被直接问"superpowers 怎么做"才查，一查就崩盘。正确顺序：查参照物→判差距→有差距才设计 |
| **2. 把"诊断成立"等同"方案成立"** | dogfooding 诊断（hooks 是盲区）本身对，但跳过了方案的独立成本/参照物检验。诊断答"哪里有张力"，方案答"值不值得解"——两步被我合并 |
| **3. 对"硬机制"盲目崇拜（原则外推）** | 用 INVARIANTS 语境的"硬拦"话术（可测信号、文档+测试双保险）外推到提交纪律（不可靠信号、fail 两难）。局部有效原则当全局原则用 |
| **4. 沉没成本拖拽** | 二审判 R1-R4 后该想"全撤"，却选"降级保留 destructive"——已写两版脚本+方案文档，本能找"能救多少"。正是 crules 批评的确认偏差 |
| **元. 草稿写成成品** | hook 脚本写成完整可粘贴形态，反向制造"方案成立"的虚假确定。dogfooding 微妙复发：crules 治"自信贴未验证文档"，方案文档自己这么干 |

### 三、4 条可复用闸口（待评估是否纳入）

任何"加机制/加约束"的方案，过这 4 关才算成立：

1. **参照物优先（Reference First）**：设计"本项目该加 X"前，先查 1-2 个成熟参照物做没做 X。没查参照物 = 不准出方案。
2. **诊断 ≠ 方案（Diagnosis ≠ Prescription）**：诊断成立不代表方案成立。方案段须独立论证收益/成本，不用诊断的精彩背书。
3. **原则不外推（Principle Scope）**：原则在语境 A 成立 ≠ 在 B 成立。外推前检查适用条件（信号是否可靠、误拦是否可接受、收益>成本）。
4. **撤回检验（Retreat Check）**：方案被打回时，**把「全撤」列入严肃候选，需证据才能以「降级保留」排除它**——不因沉没成本本能排除全撤（也不默认该撤，避免过度否决）。

**元闸口：草稿就是草稿**——未验证方案须显式标"草稿·待验证"，不得写成完整可执行形态。（crules "不虚构"红线延伸）

### 四、若纳入规则体系，候选落点（仅建议，未定）

闸口 1-4 本质是 **plan-reviewer 的前置自检缺口**——现 plan-reviewer 审"方案成品对不对"，不审"方案该不该有"。候选：在 `方案评审闭环.md`「角色四分」给**方案产出者**加出方案前的自检（① 参照物做没做 ② 解真问题还是诊断当方案 ③ 原则适用条件在吗 ④ 打回能否接受全撤）。**属新机制设计，单独 brainstorm，不顺手做**——这条本身也过闸口 1（先查其他规则包有无类似"方案前置自检"机制）。

### 五、教训一句话

> 用内部诊断（自己的哲学套自己）替代外部基准（成熟参照物怎么做），又把"诊断成立"偷换成"方案成立"——必绕弯。修正：参照物优先，诊断与方案分别独立论证，原则不外推，被打回先想全撤。

### 三、机制设计：`/review-review`（傻瓜独立复审）

**痛点**：评审文档更新后缺"独立第三方复审"环节——主控自审有确认偏差（如本次 M1 的独立性声明）。crules 有方案评审闭环（审实现方案），但没有"审评审文档"的机制。

**设计**（复用方案评审闭环的「独立第三方 + 信息隔离 + 结论不过滤」）：

新建 `commands/review-review.md`（slash command）：

1. 用户敲 `/review-review`
2. 主控读评审.md 当前态（最新详情 + 待办 + 已关闭）
3. 派**独立上下文 subagent**（`general-purpose`，`tools: Read, Glob, Grep` 只读；**不喂主对话历史，只喂评审.md**）
4. subagent 以**资深工程师**视角逐条审：
   - 落地决策是否合理（不合理→原因）
   - 合理处是否有更好方案（有→方案+原因）
   - **纪律是否真落地**（执行证据，不只看写了什么）
   - 评审.md 自身是否膨胀/滞后（dogfooding 自检）
   - 都没有→明示"可执行"
5. 返回结构化 meta-review，**主控原样呈现（不过滤）**
6. 落盘 `docs/meta-review-<日期>.md`（溯源）

**与 plan-reviewer 的关系**：结构同构（独立第三方 + 信息隔离），对象不同——plan-reviewer 审**实现方案**（可行性/漏洞/范围），review-review 审**评审文档**（决策合理性/纪律落地/自洽）。**不新建角色卡**（避免角色膨胀），用 `general-purpose` + 专门 prompt。

**独立性保证**：靠信息隔离（独立上下文 + 只喂评审.md + 结论不过滤），与方案评审闭环同一套机制——不是物理绕过主控。

**演进**：未来可泛化为 `/meta-review <文档>`（审任意决策文档：评审/方案/ADR）。初期专门化更聚焦。

> **自指闭环**：用户这次让主控做的"独立复审评审文档"，本身就证明需要 `/review-review`——因为现在主控（v16 产出者）审自己的 v16，不够独立。机制落地后，这类复审由独立 agent 做，确认偏差被结构化消除。这又是 dogfooding：crules 教别人"方案要独立第三方审"，自己的评审文档也该如此。
