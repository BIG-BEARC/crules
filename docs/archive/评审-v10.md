## §1 焦点：业务可达性误判的根因与治本方向

### 1.1 现状能做什么、做不到什么

审查与复核纪律.md 的「业务可达性 Gate」（L0/L1/L2 分级 + 禁低当高 + 查 UI 拦截 + 追生效路径 + 专家否决）：

- ✅ **能拦偷懒型误判**：没查 UI 拦截就报、停在赋值处就定级——规则给 checklist，逼审查者多走一步
- ✅ **能压定级冲动**：「代码能走通」就报 Critical——分级 + 资损克制能压住
- ❌ **拦不住无知型误判**：案例 3 个误判（称重字段后端不回传 / 核销场景无称重菜 / 数量按钮 isGray 拦截）根因都是 **AI 缺业务知识**，不是缺规则。这些"业务真相"只在需求方脑子里，**不在代码里**。

### 1.2 本质矛盾

**AI 审查者能力上限是 L1（触发条件存在）；L2（业务真实可达）不在 AI 能力范围，必须需求方确认。** 当前规则把可达性"定级"主要责任放在审查者身上（「上报前必过」「必须回答如何触发」），超出其能力——这是治标。规则是"要求"，不是"能力"：写「必须追到生效路径」≠ AI 真能追到代码之外的业务。专家否决是**事后兜底**，成本是审查噪声 + 需求方逐条否决的精力。

### 1.3 顺带：一条悬空引用

审查与复核纪律.md:113「详见 memory 中 `review-verify-business-reachability`」——该 memory 在 cutils 与模板包 memory 中**均不存在**，对模板使用者是断链。建议改成自包含（指向本方案新增的 `business-rules.md`）。

## §2 三层解法（互补，不冲突）

| 层 | 解什么 | 机制 | 状态 |
|---|---|---|---|
| **知识层（治本）** | AI 缺业务知识 → 把业务真相外化成文档，提前喂 | `business-rules.md` + 沉淀闭环（**本版重点**） | 待落地 |
| **分工层** | 规则没覆盖的新业务 → L2 判定交需求方 | 业务可达性 Gate 改「疑问单 + L2 须需求方确认」 | 待落地 |
| **流程层** | 把可达性歧义前置到方案阶段 | 方案评审闭环 plan-reviewer 加「业务假设预判」 | 待落地 |

知识层覆盖**已知的**（沉淀过的），分工层兜底**未知的**（新业务），流程层让需求方在**方案阶段**（而非实施后）确认。三层叠加才能把可达性误判压到很低。

## §3 知识层完整设计（本版重点）

### 3.1 新增载体 `memory/business-rules.md`（分域）

记忆库现有 `patterns.md`（**代码**模式）、`decisions/`（架构决策），但"称重字段后端不回传"这类是**业务真实规则**（业务实际怎么运转）——既非代码模式也非架构决策，**无处沉淀**。这正是每次都得靠需求方口头否决的根因。新增 `business-rules.md` 补这个位置。

### 3.2 一条规则的格式模板

```markdown
## WR-<域>-<序号> <一句话结论>
- **结论**：<业务实际怎么运转，肯定句>
- **可达性判定**：<审查/方案遇到什么情况 → 判 L0/L1/L2 或不可达>
- **边界 / 反例**：<什么条件下本规则不适用>
- **关联**：<相关代码路径 / 接口 / 入口；这些变更时必须回头更新本条>
- **溯源**：<何时、何场景确认的；关联的误判 case 或需求>
```

称重实例（案例 Why 的 3 个误判 → 3 条规则）：

```markdown
## WR-WEIGH-001 称重字段后端不回传
- 结论：称重接口后端【不回传】W 字段；试算回灌会清空；删菜恒走 fallback
- 可达性判定：若审查发现"代码读 W 做累加"→ L0（恒为空，不可达），降级 / 撤条
- 关联：lib/xxx/weigh_service.dart、接口 /api/weigh；后端契约变更时更新本条
- 溯源：称重审查误判 case
```

### 3.3 沉淀闭环（让文档长出来）

```
误判发生 → 需求方否决 → 沉淀进 business-rules.md
↑                                       ↓
└─ 下次同类问题，AI 读到规则，不再误判 ←─┘
```

第 1 次踩坑花需求方一次否决精力，**换来之后所有同类问题自动消音**。审查与复核纪律.md:50 已有"撤条保留一句『经确认业务不可达』"——升级为"同时沉淀一条规则进 business-rules.md"。

### 3.4 补充 SOP（想到一条规则 → 写进去 → 生效）

| 步 | 动作 | 要点 |
|---|---|---|
| ① 触发 | 4 种时机：需求方**主动想到**／审查中**否决了一条可达性发现**／**新功能上线**／**业务变更** | 最值钱是第 2 种——误判当原料 |
| ② 起草确认 | AI 可从代码/接口**推测起草**，但**必须需求方确认**才定稿 | 业务真相只在需求方脑子里；AI 起草、需求方拍板 |
| ③ 入库 | 写进 `business-rules.md`，按**域**分章节；域内编号 `WR-<域缩写>-<序号>`；顶部维护「规则索引」（编号→一句话） | 域如 称重 / 库存 / 核销 / 支付 |
| ④ 生效 | **光写不够**——必须绑「读取时机」（见 3.5），否则 AI 不知道读 | 漏了这步，文档就是死的 |

### 3.5 生效时机（关键，最易漏）

文档不会自动被读，必须把"读 business-rules.md"绑到时机：

| 时机 | 绑定到 | 效果 |
|---|---|---|
| **审查前** | 审查与复核纪律.md §业务可达性 Gate 加一步：「定级前先查 `business-rules.md`；触发条件被某条规则否定 → 直接降级/撤条」 | 命中就不报 |
| **方案评审前** | 方案评审闭环.md plan-reviewer 维度加：「审方案前对照 `business-rules.md`，业务假设与已知规则冲突 → 标红」 | 方案阶段就拦 |
| **会话级兜底** | 项目 `CLAUDE.md` / `项目附录.md` 声明：「涉及称重/库存/…域时，先读 `memory/business-rules.md`」 | 不走审查流程也先读 |

主干是前两个，第三个是兜底。

### 3.6 维护

- **更新**：每条规则写「关联代码/接口」，变更时按关联找规则同步改
- **失效不删**：业务变更使旧规则失效，标「⚠️ 已失效 + 原因 + 日期」——溯源不丢，避免重蹈
- **编号不复用**：WR-WEIGH-001 失效，新规则用 004，不回收 001

### 3.7 端到端示例（完整走一遍）

```
1. AI 审查报"代码读 W 字段累加，可能 Critical"
2. 需求方判定：后端不回传 W，不可达
3. 审查报告撤条，保留"经确认后端不回传 W，业务不可达"
4. 打开 memory/business-rules.md → 称重域 → 写 WR-WEIGH-001
5. 下次 AI 审称重代码前，业务可达性 Gate 触发读 business-rules.md
   → 命中 WR-WEIGH-001 → "代码读 W"判 L0 → 不报
```

## §6 结论

- **业务可达性知识层是继 v8 方案评审闭环后的下一个结构性增强**——它把"需求方脑子里的业务知识"外化成项目文档，让 AI 读完自己能逼近 L2，而不再每次都依赖需求方在线确认。随沉淀积累，要问需求方的越来越少。
- 三层组合（知识 / 分工 / 流程）才能把可达性误判压到很低；任一单层都不够。
- 尾巴侧：**M1（v9）+ N1/N2（v7）仍是最该先收的**，与是否落地知识层无关。
