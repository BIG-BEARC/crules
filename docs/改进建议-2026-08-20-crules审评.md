## 二、总体评价

crules 已经不是普通的 `CLAUDE.md` 提示词模板，而是一套较成熟的 AI coding 操作规程包：它把根规则、项目附录、进阶流程、agent 角色、记忆库、slash command、plugin hooks、deny-list 对抗测试和维护文档组合成一个可复用体系。

它的优势在于对 AI coding 真实失控点有深度沉淀：虚构验证、越权修改、自动提交、后台 agent 黑盒改动、方案未确认就实施、reviewer 自己动手修、记忆库漂移等问题，都有明确规则或机制约束。

它的主要短板不是规则理念，而是工程闭环：部分规则仍主要靠模型自觉执行；自动化验证和 CI 不足；部分流程偏重；跨环境、跨团队分发的稳定性还需加强。

综合判断：

- 规则理念成熟度：高
- AI coding 实战针对性：高
- 自动化验证闭环：中等
- 团队推广易用性：中等
- 安全机制完整性：中上，但仍需补 prompt injection、依赖联网和 hook 覆盖矩阵

## 三、核心优点

### 1. 根规则抓住了 AI coding 的高频风险

[`../CLAUDE.md`](../CLAUDE.md) 明确约束：先读后改、不虚构事实和证据、不自动 commit/push、破坏性操作二次确认、非平凡改动先方案确认、敏感数据安全兜底、后台 agent 完成后必须展示 diff。

这些规则直接对应 AI coding 常见事故：AI 未授权改码、未验证就宣称完成、自动提交半成品、子代理摘要被主控当结论、范围外顺手重构等。

### 2. 双 Gate 流程能抑制“直接写码”

[`../CLAUDE.md`](../CLAUDE.md) 将工作流拆为：确认范围、读取现状、需求 Gate、方案 Gate、实施、分级验证、交付汇报、提交授权。

需求 Gate 要求明确问题、预期、范围、约束、验收标准和待确认问题；方案 Gate 要求列出受影响文件、修改位置、风险、回退方式和验证方法。这比泛泛的“请谨慎修改”更可执行。

### 3. 验证证据分级成熟

[`../CLAUDE.md`](../CLAUDE.md) 区分静态证据、构建证据、测试环境证据、目标环境证据和生产证据，并禁止笼统说“已验证”。这能防止 AI 把“测试文件存在”“构建通过”“看起来没问题”误报为功能已可用。

### 4. 通用规则与项目特有信息分离合理

[`../项目附录.md`](../项目附录.md) 只承载项目名、技术栈、构建/分析/测试命令、模拟器、发布规则、隐私和硬件红线等项目特有信息。通用规则保留在 [`../CLAUDE.md`](../CLAUDE.md)，降低消费项目长期维护漂移。

### 5. 进阶能力采用渐进增强

[`../README.md`](../README.md) 与 [`../进阶/插件工作流.md`](../进阶/插件工作流.md) 都强调：根规则零依赖可用，superpowers / spec-kit 是增强层，进阶篇按场景启用。这让轻项目可以只使用根规则，大项目再启用 agent 编排、方案评审和记忆库。

### 6. reviewer / plan-reviewer 边界清晰

[`../agents/reviewer.md`](../agents/reviewer.md) 和 [`../agents/plan-reviewer.md`](../agents/plan-reviewer.md) 都锁定只读工具，强调只报不改。方案评审结论不过滤，代码审查结论需主控复核。该设计能保护审查独立性。

### 7. hooks 提供机制级安全网

[`../hooks/hooks.json`](../hooks/hooks.json) 配置了 Bash 前置 deny-list 和写入后 memory 漂移提醒。尤其 [`../hooks/deny-list.py`](../hooks/deny-list.py) 配套 [`../hooks/test_deny_list.py`](../hooks/test_deny_list.py)，沉淀了多轮红队绕过样本，明显优于只靠 prompt 约束。

### 8. 记忆库分层有价值

[`../memory/`](../memory/) 将导航、维护规则、项目模式、业务规则、技术不变量分离。尤其 [`../memory/business-rules.md`](../memory/business-rules.md) 与 [`../memory/INVARIANTS.md`](../memory/INVARIANTS.md) 分别承载业务可达性事实和硬技术约束，对长期 AI coding 很有价值。

## 四、不足与风险分级

### P0-1：一致性检查当前不是全绿

运行 `bash scripts/check-consistency.sh` 后，当前发现 [`实施计划-v47.md`](实施计划-v47.md) 有 3 个悬空链接（行 162 / 170 / 228）：

- `进阶/插件工作流.md`
- `进阶/方案评审闭环.md`
- `方案评审闭环.md`

**根因（2026-08-21 补）**：三处均为对 [`../CLAUDE.md`](../CLAUDE.md) §2/§3 与 [`../进阶/工程化流程.md`](../进阶/工程化流程.md) §4 段落的**原文引用**，引用文本里的链接是站在仓库根写的（`进阶/...`），落到 `docs/` 下相对路径即悬空。

这说明项目门禁能发现真实问题，但当前仓库没有保持全绿。对一个强调验证证据的规则包，这是最高优先级的 dogfooding 问题。

**修法二选一**（不建议无脑改成 `../进阶/...`——会让引文与原文不一致）：

1. 引用段内的链接转纯文本路径（反引号），改动最小；
2. v47 四批次已落地，[`实施计划-v47.md`](实施计划-v47.md) 按项目惯例本就到归档时机——移入 [`archive/`](archive/)（一致性脚本 A 查本就豁免 archive），一石二鸟。

### P0-2：一致性脚本发现问题后不以非零退出

[`../scripts/check-consistency.sh`](../scripts/check-consistency.sh) 当前会打印问题，但整体仍输出完成——实测发现 3 处悬空链接时退出码仍为 0。若直接接入 CI，可能出现“发现问题但 CI 仍绿”。AI 也可能只摘最后的“完成”而误报通过。

**建议：**脚本维护失败计数；任一 FAIL 最终 `exit 1`；最后一行明确输出 `PASS` 或 `FAIL N`。

### P0-3：缺少 CI，门禁靠人工记得跑

当前仓库未见 CI 配置。可执行门禁主要是 [`../scripts/check-consistency.sh`](../scripts/check-consistency.sh) 与 [`../hooks/test_deny_list.py`](../hooks/test_deny_list.py)，但没有自动挂到 CI。

[`待办.md`](待办.md) 已记录 V1 “CI 挂一致性脚本与 fixture 回归”，说明该缺口已被项目识别但尚未实施。

**建议：**CI 不另立条目，直接实施待办 V1（已登记 🔴）；命令集可把 `python3 -m py_compile` 吸收进 V1：

```bash
bash scripts/check-consistency.sh
python3 hooks/test_deny_list.py
python3 -m py_compile hooks/deny-list.py hooks/test_deny_list.py hooks/pending-updates.py
```

### P0-4：仓库缺少 `.gitignore`，对 `.claude/settings.local.json` 的保护不随仓库走

项目目录下存在 `.claude/settings.local.json`，其中含本机权限 allowlist、绝对路径和疑似敏感外部 URL。

**事实核验（2026-08-21 修正初版表述）**：该文件当前已被本机全局配置忽略（实测 `git check-ignore -v` → `~/.gitignore_global:4: **/.claude/settings.local.json`），本机无误提交风险；但 **crules 仓库本身没有 `.gitignore`**——保护依赖作者本机配置，换机器开发或他人克隆后即失效。

**建议：**新增仓库级 `.gitignore`，收录 `.claude/settings.local.json`、`.claude/worktrees/` 等；文件内 URL 是否清理 / 轮换由需求方判断（涉内容审阅，本报告不读取其内容）。

### P1-1：工具能力和 Claude Code 环境耦合较强

规则中直接引用 `AskUserQuestion`、`EnterPlanMode`、`ExitPlanMode`、`Agent`、`Glob`、`Grep` 等工具名。不同 Claude Code 版本、Agent SDK、自定义 agent 或工具受限环境中，这些工具未必可用。

**建议：**新增工具能力降级表：首选工具不可用时，改用文本确认、只读 Bash 搜索、串行执行或显式说明无法并行。

### P1-2：slash command 是说明书型，不是确定性 CLI

[`../commands/crules-init.md`](../commands/crules-init.md) 与 [`../commands/update-memory.md`](../commands/update-memory.md) 本质是 Markdown 流程说明。v42 已为老项目分支加了指令级硬护栏（git 干净树检查 + 时间戳备份 + 冲突体检 + 逐条裁决 + 资产禁覆盖），非真空；但这些步骤的执行仍依赖模型遵守。

**建议（定位为增强而非补缺）：**为 `/crules:crules-init` 增加 dry-run 报告机制：列写入目标、现有文件、冲突、备份、推荐安装模式；老项目默认只出报告，不自动覆盖。

### P1-3：hook 是黑名单安全网，不是沙箱

[`../hooks/deny-list.py`](../hooks/deny-list.py) 已诚实声明黑名单无法穷尽。当前仍无法覆盖脚本间接执行、`python -c` 删除文件、`find -delete`、`chmod -R`、`chown -R` 等高风险操作。

**建议：**增加 hook 覆盖矩阵，明确哪些由 hook 拦截，哪些仍依赖 prompt、原生权限确认或人工执行。

### P1-4：`error` agent 可写权限与“诊断默认不改码”存在张力

[`../agents/error.md`](../agents/error.md) 配置了 Edit / Write，并在流程中写“用 Edit 修改文件”。但 [`../CLAUDE.md`](../CLAUDE.md) 规定故障诊断默认不改码，除非明确要求修复。

**建议：**拆分 `error-diagnoser` 与 `error-fixer`，或在 `error.md` 顶部增加硬约束：未明确要求修复时只诊断不写入。

### P1-5：大需求派审的 Gate 疲劳——裁决项，撤回直接建议

~~建议引入风险分级~~ **撤回**：核验发现「默认必须派审」是 2026-08-20 需求方刚裁定的决议（[`优化方案-v47.md`](优化方案-v47.md) §十 消解表 #6），初版报告未引用该在先裁定即建议反向修改，属方法论失误。且「分级降摩擦」思路与待办 V3（Gate 信任分级）同主题。

**保留为裁决项**：若后续实战出现 Gate 疲劳实证（确认点被橡皮图章式跳过），与 V3 合并做一轮 brainstorm（信任分级 vs 风险分级两机制对比）；在此之前维持现行裁定。

### P1-6：提交策略默认 push——定位决策，需裁决而非缺陷

「commit 后默认 push」是需求方明确规则（[`../CLAUDE.md`](../CLAUDE.md) §2），对当前个人包定位是**既定设计**而非缺陷。仅当 crules 转向通用团队模板时才成为问题：团队可能要求本地提交后开 PR，或受保护分支不允许直接 push。

**裁决项**：若定位转向通用模板，改为 `commit` 只本地提交、`push` 才推送、`提交并推送` 才执行完整流程，默认策略放 [`../项目附录.md`](../项目附录.md) 覆写；维持个人包定位则不改。

### P1-7：“修一坑查同类”可能扩大范围

[`../CLAUDE.md`](../CLAUDE.md) 同时要求守住范围边界和修一坑查同类。两者都正确，但需要明确边界。

**建议：**改为：修一坑后必须检索同类；同范围内一并处理，范围外只报告并请求确认。

### P1-8：缺少 prompt injection / 不可信内容规则

当前规则有不虚构、敏感数据兜底，但缺少明确的 prompt injection 防护：仓库文件、日志、网页、issue、PR 评论、子代理输出中的指令都应视为数据，不能覆盖系统 / 用户 / 根规则。

**建议：**在 [`../CLAUDE.md`](../CLAUDE.md) 协作红线中加入不可信内容规则。

### P1-9：依赖、联网、供应链策略不够明确

部分已有（[`../CLAUDE.md`](../CLAUDE.md)「敏感数据安全兜底」禁外发、「最小必要改动」禁顺手升级依赖），缺口聚焦在：**新增依赖的确认流程、明确要求升级时的影响面说明、`curl | bash` / 下载脚本 / 访问外部服务的确认边界、license 与 supply chain 风险提示**。

**建议：**新增“外部依赖与网络操作”小节：新增/升级依赖前说明理由、影响和回退；下载脚本或访问外部服务需确认；敏感代码和生产数据不得外发。

### P2-1：跨包链接和复制拓扑仍有断链风险

多处通用文档引用 `../../flutter/checklist.md`。在 crules 源仓库中可能成立，但复制到消费项目后，尤其 agents / memory 下沉到 `.claude/` 后，相对路径会变化。[`待办.md`](待办.md) 已记录 N5 “复制后相对路径断链”。

**建议：**与待办 N5 合并处理（不另立条目）——通用包内减少跨包相对链接，改成“若安装 Flutter 规则包，读取其 checklist”；本报告增量「一致性脚本增加部署拓扑模拟检查」并入 N5 范围。

### P2-2：版本口径较多

当前同时存在 plugin semver `0.2.2`、docs 轮次 v44/v47、README v47 口径和 CHANGELOG 顶部 v44。对新维护者不直观。

**建议：**新增版本说明：plugin semver 是分发版本，docs vN 是内部评审/优化轮次，CHANGELOG 只记发布级能力变化。

### P2-3：默认中文回复——定位决策，需裁决

[`../CLAUDE.md`](../CLAUDE.md) 规定“必须始终中文回复”。这适合当前作者个人使用；与 P1-6 同属定位决策：若转向通用团队模板，建议默认“使用需求方语言”，中文作为项目覆写；维持个人包定位则不改。

### P2-4：memory 模板偏 Flutter / 移动端，新手容易误用

[`../memory/NAVIGATION.md`](../memory/NAVIGATION.md) 示例里有 widget、view、provider、Flutter checklist 等术语。虽然已有说明要求非 Flutter 项目替换，但新手可能直接保留，导致记忆库无效。

**建议：**与待办 D8 合并处理（D8 已点名「NAVIGATION 术语表」为 v18-D 同类漏网，不另立条目）；Memory Lite / Full 分档与 v18-C（memory git 分层）属相邻主题，可一并 brainstorm；初始化时明确“示例必须替换，不替换视为未启用”。

## 五、解决方案路线图

### 阶段 1：先硬化现有门禁（顺序锁定：C2 → C1 → V1）

1. **先**修改 [`../scripts/check-consistency.sh`](../scripts/check-consistency.sh)：失败计数 + `exit 1` + 末行 `PASS` / `FAIL N`（否则 CI 接上去也是假绿）。
2. **再**修复 [`实施计划-v47.md`](实施计划-v47.md) 的 3 处悬空（修法见 P0-1 二选一）。
3. **CI 直接实施待办 V1**（不另立条目），把 `python3 -m py_compile hooks/*.py` 吸收进 V1 命令集；可选新增 `scripts/verify.sh` 统一入口。
4. 新增仓库级 `.gitignore`（见 P0-4）。

### 阶段 2：把高风险流程变成可检查流程

1. 为 `/crules:crules-init` 增加 dry-run 报告机制。
2. 增加 plugin 发布脚本，覆盖版本同步、verify、plugin update、cache grep。
3. 落地规则行为探针集，覆盖未授权不得 commit、只贴报错不得改码、方案 Gate 停顿、ExitPlanMode 后落盘等。
4. 增加部署拓扑链接检查。

### 阶段 3：降低团队推广摩擦

1. README 增加 Lite / Team / Advanced 三档。
2. 新增 QUICKSTART，面向新手说明日常 5 条。
