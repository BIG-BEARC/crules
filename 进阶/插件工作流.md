# 插件工作流

> **启用条件**：项目安装了 spec-kit 和/或 superpowers 时，本篇给出它们与本包双 Gate 工作流的映射。
> 被 [`../CLAUDE.md`](../CLAUDE.md) §3、[审查与复核纪律.md](审查与复核纪律.md)、[工程化流程.md](工程化流程.md)、[Agent编排.md](Agent编排.md) 各篇引用。

---

## 定位

本包的工作流（需求 Gate → 方案 Gate → 实施 → 验证 → 评审）与 spec-kit / superpowers 的 skill **不是替代，是映射**：同一阶段，启用插件时用对应 skill，不启用时用 Claude Code 内置能力兜底。两层共存不冲突。

---

## 阶段映射表

| 阶段 | 内置兜底（零依赖） | 启用 superpowers | 启用 spec-kit |
|---|---|---|---|
| 需求 Gate | `AskUserQuestion` 澄清六要素 | `brainstorming`（HARD-GATE：未批准禁写码） | `/speckit` 产出 spec / constitution |
| 方案 Gate | `EnterPlanMode` 出计划 + `ExitPlanMode` 获批 | `writing-plans` | constitution 约束方案 |
| 实施 | 直接写 | `test-driven-development`（红绿重构） | spec-kit 的任务产出命令（子命令名以已装版本为准） |
| 验证 | 手动跑 analyze + test 贴输出 | `verification-before-completion`（强制贴输出） | — |
| 评审 | 自查对照 checklist | `requesting-code-review` | — |
| 多 agent | `Agent` 工具派发 | `subagent-driven-development` | — |
| 调试 | 读日志定位 | `systematic-debugging` | — |

> 不启用任何插件时，本表「内置兜底」列即完整工作流——本包不硬依赖插件。

## 选 superpowers 还是 spec-kit

两者在「需求 / 方案」阶段**功能重叠**（都做需求澄清与方案），是两种方法论，**选一个为主，不是叠加**：

| | superpowers | spec-kit |
|---|---|---|
| 风格 | 对话驱动，需求在探索中清晰 | spec 文档驱动，先正式规约再实现 |
| 需求 | `brainstorming`（交互澄清） | `/speckit`（产出 spec / constitution） |
| 方案 | `writing-plans`（实现计划） | constitution 约束 + 任务产出 |
| 适合 | 需求待探索、流程轻、重 TDD | 需求要正式化、作契约、变更受控 |

三种用法（任选）：

1. **全程 superpowers**：brainstorming → writing-plans → TDD → review
2. **全程 spec-kit**：`/speckit` 产出 spec → 基于 spec 实现
3. **混搭（分工别重复）**：如 spec-kit 做需求 Gate（产出 spec）+ superpowers 做方案 / 实施（writing-plans + TDD）。**禁止** brainstorming 与 `/speckit` 同时做需求澄清——两套都澄清一遍就是重复。

> 怎么指定：在 [`../项目附录.md`](../项目附录.md) 声明（如「本项目需求用 spec-kit，实施用 superpowers」），或当场告诉 AI。装了不代表都要用——指定哪个子集就用哪个。

## 优先级与冲突

- **提交**：本包 [`../CLAUDE.md`](../CLAUDE.md) §2 的人工提交**压过** superpowers 的自动 commit。优先级链：需求方指令（CLAUDE.md）> skill > 默认行为。
- **Gate 不被绕过**：启用插件时，skill **增强** Gate（如 brainstorming 把需求讨论做扎实），但**不绕过**——仍须需求方明确确认才进下一阶段。
- **spec-kit 与 superpowers 互补**：spec-kit 管 spec（需求 / constitution），superpowers 管流程编排，两者分工不重叠。
