# Agent 编排

> **启用条件**：使用多 agent 协作时复制本篇 + 配套 `agents/` 目录（部署位 `.claude/agents/`）。单人单 agent 工作不需要本篇。
> 配套根规则：[`../CLAUDE.md`](../CLAUDE.md)。本篇不重复根规则（提交、范围、后台 diff 展示等），只定义角色分工与调度。
> 启用 superpowers / spec-kit 时，多 agent 阶段的 skill 映射（如 `subagent-driven-development`）见 [`插件工作流.md`](插件工作流.md)。
>
> **术语**：本篇「主控」指分发任务的 agent（通常即主对话）；「子代理」指被派发的 agent。模型档位按任务难度选型，不写死——难度越高用越强模型。

---

## 主控：主对话本身

主控即**主对话**（直接与需求方对话的 agent），不是独立子代理。主控负责需求讨论、方案设计、任务拆分与分发，并按改动规模分档决定「分发」还是「直接做」。

### 主控职责分档

| 改动规模 | 主控做法 |
|---|---|
| 极简（单字段、文案、明显单点修复） | 直接写，不走分发 |
| 单域小改（仅触及一个角色领域） | 可直接写，或派该域子代理 |
| 大改 / 跨域 / 多模块 / 需方案设计 | **只做设计与分发，不写实现**——拆子任务派给对应子代理，自己负责汇总与校验 |

### 主控无论如何都要做

- **必须**先与需求方讨论并确认方案（根 [`../CLAUDE.md`](../CLAUDE.md) §3 双 Gate），确认后才动手或分发
- 不得在需求方未确认时擅自开始实现
- 分发后负责汇总：`git status` + `git diff`、agent 摘要与实际 diff 对照、编译校验（见下方「编排执行规范」）

> 「大改只分发不写」不是绝对禁令，是按规模分档的纪律——极简改动主控直接写更高效。判断标准看改动规模，不看身份。

## 可用 Agent 模板

**通用角色**（`agents/`，部署位 `.claude/agents/`，任意技术栈）：

| Agent | 任务难度 | 主责 |
|---|---|---|
| **主控**（主对话） | 高 | 需求讨论、架构设计、拆分分发；大改只分发、极简直接写（见上） |
| `error` | 中 | 运行时错误、崩溃、编译异常排查 |
| `reviewer` | 高 | 代码 Review、质量检查（只报不改） |

**技术栈专属角色**（按技术栈到对应子目录；Flutter 见 Flutter 规则包（crules 模板包同级 `../flutter/agents/`，未安装则忽略；非该技术栈项目用不到））：

| Agent | 任务难度 | 主责 |
|---|---|---|
| `frontend` | 中 | 页面 UI、布局、组件、动画、交互 |
| `backend` | 中 | 业务逻辑、状态管理、数据层、网络层、模型 |
| `i18n` | 低 | 多语言翻译、文案 Key 管理 |
| `platform` | 中 | 原生 / 平台特定代码、平台桥接 |

> `plan-reviewer`（`agents/plan-reviewer.md`）属**方案评审子系统**（实施前审方案，见 [`方案评审闭环.md`](方案评审闭环.md)），**不参与代码实现编排**，故不在上表的实现角色列。

主控即主对话，无独立文件；通用角色的文件在 `agents/`（部署位 `.claude/agents/`），技术栈专属角色在对应技术栈子目录。

## 主责判定

`frontend` 和 `backend` 是两个主力，覆盖绝大多数代码实现：

| 任务特征 | 主责 |
|---|---|
| 新建页面、大量样式改动、重构界面、组件开发 | `frontend` |
| 业务逻辑、数据层、网络接口、状态管理、模型 | `backend` |
| 跨层架构调整 / 大规模重构 / 方案设计 | 主控（设计）+ 其他（执行） |
| 多语言文本 | `i18n` |
| 原生 / 平台代码 | `platform` |
| 报错排查 | `error` |
| 代码 Review | `reviewer` |

### 允许的跨域修改

为完成闭环，主责 agent 可跨域做少量改动：

- `frontend` 为页面闭环，可改少量页面级状态和强相关业务逻辑
- `backend` 为功能闭环，可改少量 UI 接入、事件绑定、页面联动
- **跨域修改超过 3 个文件**且属同类结构调整，**必须**先由 主控 评估

## 任务拆分与调度

**串行（有依赖）**：主控 设计数据层 → `backend` 实现 → `frontend` 接入 UI；代码完成 → `i18n` 补翻译 → `reviewer` 审查。

**并行（无文件冲突、无依赖）**：`frontend` 写页面骨架 + `backend` 写业务/数据层同时进行；`i18n` 补翻译 + `reviewer` 审查同时进行。

---

## 调用约定

- 调用子代理**默认后台执行**（`run_in_background: true`）
- 启动后**必须立刻**回一句类似「已在后台开始 XX 任务，你可以等待结果或讨论其他工作」
- 只有以下情况走前台（阻塞），且**必须主动说明原因**：① 极简任务（预计 10 秒内）② 有严格依赖 ③ 需求方明确要求立即出结果
- 子代理完成时以 `<task-notification>` 回传，下一轮汇总给需求方

## 主控复核责任（审查 / 调查任务）

多 agent 协作完成**审查或调查**时，主控对子代理的发现负复核责任：

- 子代理结论是【线索】，不是结论
- 主控上报前**必须**亲自读关键代码确认触发条件，不得整段搬运子代理输出作为最终结论
- 详见 [`审查与复核纪律.md`](审查与复核纪律.md) 的「子代理与工具结论复核」

### 协作纪律

- 每个执行者**只能修改明确分配给自己的文件**
- 共用工作区时，**不得覆盖、回滚或清理**其他执行者的改动
- 存在前后依赖的工作**必须**顺序执行

---

## 编排执行规范

1. 收到需求 → 主控 做需求讨论与方案设计
2. **需求方明确确认后**才进入下一步
3. 主控 输出拆分计划（各子任务、依赖关系、执行顺序）
4. 按策略调度对应 agent 执行
5. 所有 agent 完成后，主控 依次执行：
   - `git status` + `git diff`（含 staged / unstaged）把实际改动摆给需求方审阅
   - 把 agent 摘要与真实 diff 逐项对照，标注差异或遗漏
   - 运行编译校验，把结果一并反馈
6. 需求方确认无误后，等 `commit` / `push` / `提交` 指令才执行完整提交流程（见 [`../CLAUDE.md`](../CLAUDE.md) §2）
