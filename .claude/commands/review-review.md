# /review-review

对评审文档（默认 `docs/评审.md`）做**独立第三方复审**。解决主控自审的确认偏差——主控既写评审又改代码，自审倾向肯定自己。

> **与 `/crules-init`、`/update-memory` 的区别**：那两个改代码 / 索引；本命令**只审不改**——审的是评审文档本身（决策合理性 / 纪律是否真落地 / 自洽性 / 是否膨胀滞后），产出 meta-review 报告。

## 为什么需要

`docs/评审.md` 记录每轮评审的落地决策。但落地由主控执行，落地记录也由主控写——**「我说我做了」缺独立核验**。这正是 crules 教别人「方案要独立第三方审」（见 `进阶/方案评审闭环.md`）的**自指缺口**：crules 有审实现方案的 `plan-reviewer`，却没有审评审文档的机制。本命令补这个缺口。

> **自指闭环（dogfooding）**：crules 教「约束光文档没用，要机制硬拦」「方案要独立第三方审」——本命令把这两条套回 crules 自己的评审文档。

## 机制（复用方案评审闭环的信息隔离）

| 要素 | 取值 | 来源 |
|---|---|---|
| 独立上下文 | subagent 看不到主对话历史 | 方案评审闭环「技术边界」 |
| 只读 | `tools: Read, Glob, Grep`（无 Edit/Write/Bash 写性） | plan-reviewer 角色卡 |
| 结论不过滤 | subagent 返回值由主控**原样呈现 + 原样落盘**，不修改/不筛选 | 方案评审闭环「落盘约定」 |
| 抽查源文件 | subagent **可且应当**读 crules 源文件核验评审.md 的「已落地」声明（不只信评审.md 自报）| **本命令加强**（见下） |

### 为什么 subagent 必须能抽查源文件

plan-reviewer 只审一个方案成品（读 PRD 即够）；但 review-review 审的评审.md 含「X 已落地」这类**对现实的声明**——若 subagent 只读评审.md，它只能信主控自报，**独立意义归零**。故 subagent 输入是「评审.md + 全 crules/ 读权限」，prompt 明确要求**抽查**：评审.md 说「commands/ 已补」，subagent 就该 `grep commands crules/README.md` 验证。

## 执行步骤

1. 主控读 `docs/评审.md` 当前态（最新详情 + 已关闭 + Changelog）+ `docs/待办.md` 当前态（v44 起待办池拆出，评审只记轮次）+ `docs/五维基线.md` 当前态（v63 起五维雷达）
2. 派**独立上下文 subagent**（`general-purpose`，prompt 只喂评审.md + 待办.md 当前内容 + crules/ 读路径，**不喂主对话历史**）
3. subagent 以**资深工程师**视角逐条审：
   - **落地决策是否合理**：不合理→给原因（如该升🔴的降了 / 该改的标不动没说清代价）
   - **合理处是否有更好方案**：有→给方案+原因
   - **纪律是否真落地**（核心）：评审.md 声称「已落地」的项，**抽查源文件**核验（不只看写了「✅」）；尤其盯 L14「总览同步检查」是否真复查留痕
   - **评审.md 自身健康**：是否膨胀（详情堆太多轮）/ 滞后（已落地项仍列待办）/ 编号笔误
   - **范围是否扩大**：本轮改动 / 评审是否夹带已确认需求之外的项（对照 CLAUDE.md「守住范围边界」）
   - **五维基线滞后吗**（v63 起）：雷达评分与仓库现状脱节（如机制化声明与实际能力不一致——error.md 教训）→ 给修订分 + 依据；**重评结论由 subagent 给出，主控只原样落盘不自改**（铁律 2）
   - 都没有问题→明示「vN 落地可执行，无需调整」
4. subagent 返回结构化 meta-review（分 ✅合理 / 🔴不合理 / 🟡可商榷 / 🟢笔误 四类）
5. 主控**原样呈现**给需求方（不过滤、不转述为温和措辞）
6. 落盘 `docs/meta-review/meta-review-<YYYY-MM-DD>.md`（溯源；同日多次追加 `-2`、`-3`）
7. 主控据 meta-review 评估并落地（合理→执行；不合理→指出原因），等需求方确认

## 输出格式（subagent 返回，主控原样落盘）

```markdown
# meta-review · <日期> · 审 <评审.md 轮次>

## 独立性声明
本复审由独立上下文 subagent 做（看不到主对话历史，只读评审.md + 抽查源文件）。

## ✅ 合理（含精彩处）
| 决策 | 评价 |

## 🔴 不合理 / 可商榷
| # | 问题 | 建议 |

## 🟢 笔误 / 小项

## 抽查核验（纪律落地证据）
| 评审.md 声称 | 源文件核验 | 一致? |

## 结论
（vN 落地可执行 / 需调整 N 项）
```

## 与 plan-reviewer 的关系

**结构同构，对象不同**：

| | plan-reviewer | review-review |
|---|---|---|
| 审什么 | 实现方案（可行性/漏洞/范围） | 评审文档（决策合理性/纪律落地/自洽） |
| 时机 | 实施前 | 评审.md 更新后 |
| 复用 | — | 独立第三方 + 信息隔离 + 结论不过滤（同一套机制） |

**不新建角色卡**（避免 agents/ 角色膨胀）——用 `general-purpose` + 本命令 prompt 承载视角，比专门角色卡轻。

## 依据

- 信息隔离机制：`进阶/方案评审闭环.md`「技术边界」「落盘约定」
- plan-reviewer 角色：`agents/plan-reviewer.md`（工具锁 / 只读 / 结论不过滤）
- dogfooding：crules 套用自己教的「方案独立第三方审」

## 注意

- `/review-review` **只审评审文档，不改被审的落地代码**（落地由主控据 meta-review 另做，且需需求方确认）。
- **不替代方案评审闭环**：那审实现方案，本命令审评审文档，对象不同。
- 抽查是关键——subagent 只读评审.md 不算独立，必须核验源文件。
- 演进：未来可泛化为 `/meta-review <文档>`（审任意决策文档：评审/方案/ADR）。初期专门化更聚焦。
